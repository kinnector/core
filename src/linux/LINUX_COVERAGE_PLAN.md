# Linux coverage plan for `core/` — gap analysis + punch list for Antitheft

Written while working on Linux — unlike the Windows/macOS plans in the sibling directories, this one *can* be executed and tested in the same environment it was written in. It's plan-only for now by explicit choice (kept parallel to the Windows/macOS handoff docs rather than implemented immediately), not because of any build/test limitation. Pick this up as a normal implementation task, verifying each step against a real kernel as you go — see "Verification" per phase below.

**Read `kinnector.dev/antitheft/antitheft.md` first**, specifically §3's Linux subsection, §4 (storage-ownership + lineage-marker propagation, including the concrete Linux mechanism already spec'd there — `sched_process_fork` + `bprm_check_security`, composite `(pid, start_time)` keying), and §7 (config domain). This doc assumes that context and doesn't repeat the design rationale.

## Bottom line

`core/`'s Linux side is structurally far more mature than Windows — it already has real, synchronous, kernel-level **deny** capability via BPF LSM hooks (40+ distinct `-EACCES`-class deny sites across `file_open`, `file_permission`, `bprm_creds_for_exec`, `ptrace_access_check`, `task_kill`, `file_mprotect`, `path_chmod`), not a detection-only engine. `blocking_enabled` (config_map index 0) gates real synchronous denials today.

**But graded precisely against Antitheft's actual promise ("is the process touching this resource the one process allowed to touch it? if no, refused before it completes"), the core mechanism is missing**: the kernel path checks a protected file's category against the accessing process's *generic trust level*, never against an *owner allowlist* for that specific resource. There's no kernel-side concept of "this process may touch `wallet`-category files but not `ssh_material`-category files." A generically-trusted process can read any sensitive-category file freely; an untrusted process is blocked from all categories uniformly. Building that owner-vs-resource match into `file_open`/`file_permission` is the single highest-value item below — everything else is either near-free activation of already-written dead code, or supporting infrastructure.

## Critical constraint — this file is shared production code, not Antitheft's own sandbox

**Read this before touching any phase below.** `kinnector.bpf.c` and `ebpf_loader.cpp`/`ffi.cpp`'s `g_loader` singleton are not Antitheft-owned. `/home/user/Documents/kinnector/kinnector-core` is a plain symlink to `core` (confirmed via `file`/`diff` — identical content, not a fork or a stale copy), and **both `wardend` and `antitheft-agent` build from this exact same `kinnector.bpf.c`** — `warden/build.rs` statically links `libkinnector-core.a` built from `core/build/lib`; `antitheft-agent/build.rs` dylib-links `libkinnector-core.so` from the same source tree via the `kinnector-core` symlink. There is only one compiled policy engine, one `EbpfLoader` class, one `g_loader` global in `ffi.cpp`.

This file is already Warden's real production enforcement logic, not neutral collection substrate — despite the top-level workspace `CLAUDE.md` describing `core/` as "collection only." `fw_rules_v4/v6`, `db_outbound_allowlist`, `infra_outbound_allowlist`, `sshd_uid` checks, `host_mnt_ns`/`host_pid_ns` container-escape detection, and `protected_static_inodes` web-root protection all live directly in the same LSM hook functions this plan's Phase 1/3/5 need to touch (`file_open`, `file_permission`, `ptrace_access_check`, `task_kill`). `warden/src/trust.rs` says outright: "`core/src/linux/ebpf/kinnector.bpf.c`: every one of those LSM hooks" makes "essentially every local enforcement decision wardend/core makes."

**Verified: no isolation mechanism exists today.** There is no product/consumer/deployment-mode flag anywhere in `ebpf_loader.h`'s config surface, and `antitheft-agent` calls the identical `initialize_telemetry_engine` FFI entry point Warden uses, with zero `kinnector-config`/`protect-community/configs/warden` wiring of its own to even distinguish itself. Regression coverage for this file is thin: `test_lsm.cpp` + `test_ebpf_loader.cpp` total 187 lines — not enough to reliably catch a Warden behavioral regression introduced while extending this file for Antitheft.

**Practical implication — this is a shared-build regression risk, not a live runtime collision.** Warden runs on servers/containers; Antitheft runs on end-user consumer machines — the two products never load this object on the same host, so there's no risk of them fighting over the same running kernel state. The real risk is that both binaries compile from the same source tree: a bug introduced into a shared hook function while building Antitheft's owner-allowlist logic ships into Warden's next build too, silently, with no consumer-specific isolation to contain the blast radius.

**Required approach for every phase below that touches `kinnector.bpf.c`:**
1. Add an explicit `deployment_mode` value to `config_map` (e.g. `MODE_WARDEN` / `MODE_ANTITHEFT`), set once by whichever binary calls `initialize_telemetry_engine` (mirrors the existing pattern of other single-purpose `config_map` switches like `blocking_enabled`/`host_mnt_ns`). Any new Antitheft-only branch (owner-allowlist checks in Phase 3, generalized ptrace/task_kill protection in Phase 5) must be gated behind `mode == MODE_ANTITHEFT`, appended after Warden's existing checks, never interleaved with or replacing them — so a Warden deployment executes the exact same code path it does today, with the new branch compiled in but never taken.
2. Never reuse or repurpose a map/config index Warden's existing logic reads (`config_map`, `process_threshold_map`, `trusted_ancestor_roots`, `sensitive_inodes_map`, `protected_static_inodes`, `bypassed_directories`, `fw_rules_v4/v6`, `db_outbound_allowlist`, `infra_outbound_allowlist` are all Warden-owned) — new Antitheft state goes in new maps (e.g. Phase 3's `resource_owner_map`, Phase 5's `protected_owner_pids`).
3. Before merging any change to this file, build and run `wardend`'s own test/verification path against it (`test_lsm.cpp`, `test_ebpf_loader.cpp`, plus whatever manual server-side smoke test Warden currently relies on beyond those 187 lines) to catch a regression the thin existing suite might not — this is a mandatory step this plan didn't originally call out, add it to each phase's test criteria below, not just Antitheft's own test.

Phases 1 and 3 below are the two that actually touch shared hook functions/attach points; their steps are revised accordingly. Phase 5 also touches shared functions (`ptrace_access_check`/`task_kill`) and needs the same gating.

## Verified current state

- **`ebpf/kinnector.bpf.c`** defines 47 `SEC(...)` programs. Cross-referenced against `ebpf_loader.cpp`'s `LoadAndAttachLsm()` (`:334-391`) and `LoadAndAttachFallback()` (`:393-447`): **six are compiled but never attached**, including the two that matter most for Antitheft:
  - `tracepoint_sched_process_fork` (`kinnector.bpf.c:2280`) — copies `pid_tree_type_map`, `process_threshold_map`, `trusted_ancestor_roots`, `jvm_exception_pids`, `admin_session_pids` from parent to child at fork time. **This is exactly the §4-required lineage-marker propagation mechanism, already written, just never wired up.**
  - `mmap_file` (LSM, `:2092`) — emits image-load telemetry on every executable file-backed mapping (SO sideload into a process), directly the injection-into-owner-process signal §3/§10 calls for.
  - (The other four — `warden_sb_mount`, `warden_path_chroot`, `tracepoint_sys_enter_setns`, `tracepoint_sys_enter_unshare` — are container-escape/server-security only, not Antitheft-relevant, but confirm the attach-coverage gap is general, not isolated to these two.)
  - A sibling codebase, `core-pro/src/pro.bpf.c` + `core-pro/src/ebpf_pro.cpp`, *does* attach an equivalent fork-propagation program — but Antitheft has no Pro/OSS split (see `antitheft.md` §8), so this logic needs to be ported into `core/`'s own object/loader, not depended on as-is.
- **§4 lineage-marker propagation, graded piece by piece**: root-mark stamping on package-manager-binary exec (`is_install_binary()`, `bprm_creds_for_exec:1467-1484`) is real and attached — this part works today. Fork-time propagation exists in source but is dead (above). The composite-key discipline is **partially violated**: `pid_tree_type_map` (`:238-243`) is keyed on raw `uint32_t pid`, not the `process_key {pid, start_time}` struct that `process_threshold_map`/`trusted_ancestor_roots` correctly use elsewhere in the same file — meaning a since-exited npm-descended process's install-context stamp can currently be inherited by an unrelated new process reusing that PID, under exactly the fork-bomb-y install-script churn the design doc warns about. And `is_install_binary()`'s package-manager list is hardcoded strings in the `.bpf.c` file, not sourced from the `PackageManagerContext` config (§7) — adding a new ecosystem today requires a kernel-object rebuild.
- **Storage-ownership enforcement — the central gap**: `file_open` (`:1032-1056`) looks up `sensitive_inodes_map[ino]` for a `category`, but only ever uses that category for later heuristic *scoring* (`:1058-1065`) — the actual deny check (`:1038-1056`) is purely "is this process globally untrusted / in an install session," with no comparison against an owner set. `file_permission` (`:1092-1125`) does the identical pattern for write-protection. The one place an owner-vs-resource match *does* exist is `antitheft-agent/src/heuristics.rs:703-735` ("Zero-Tolerance Vendor Ownership Rule," substring-matching vendor names like `exodus`/`discord`/`keyring`/`kwallet`/`ssh` between the file's path and the process's image path) — but it runs in userspace, off telemetry emitted *after* `file_open` already allowed the read, and reacts via `suspend_process_tree` (`:912+` — a `wall` broadcast + tmux popup + `antitheft-cli triage` prompt). That's Warden-server-EDR alerting shape, not a transparent pre-completion deny, and is exactly the kind of legacy logic `antitheft.md` already told us to reconcile file-by-file rather than assume reusable.
- **`ptrace_access_check`/`task_kill` owner-process protection**: the *mechanism* Antitheft needs (deny ptrace/signal against a protected process unless the requester is privileged) is proven and working today (`:1899-1948`, `:1950-2009`) — but it's scoped to `TREE_ADMIN_SESSION` processes and a hardcoded `"warden"` comm-string match, not a configurable "this PID is the owner process for a protected credential-manager binary" concept. The plumbing pattern to generalize this already exists twice over in the same file.
- **Canonical resource identity**: already correct in principle — every check resolves to `struct inode` → `i_ino`, not path strings, which inherently defeats symlink/hardlink path-string bypass. The one gap: it's raw inode number alone, not the `(dev_t, inode)` composite — fine on a single filesystem, ambiguous across bind-mounts/multiple filesystems with overlapping inode ranges.
- **`fanotify.cpp`** is FIM-only — `FAN_CLASS_NOTIF` init, `FAN_MODIFY | FAN_CLOSE_WRITE`, no `FAN_OPEN_PERM`/`FAN_ACCESS_PERM`/`FAN_CLASS_PRE_CONTENT` anywhere, and the code only ever `read()`s the fanotify fd, never `write()`s an allow/deny response. Lower priority than the eBPF LSM gap above since real blocking already exists via LSM — worth doing only as belt-and-suspenders for kernels without BPF LSM support.
- **Linux's DPAPI-equivalent — GNOME Keyring / KWallet's Secret Service D-Bus API — has zero coverage anywhere**, and isn't even flagged as residual risk in `antitheft.md` the way Windows' DPAPI gap is. A logged-in-user-context process can call `Secret.Service.Unlock`/`OpenSession` on the same keyring a legitimate app would, exactly analogous to `CryptUnprotectData` on Windows. This needs the same explicit "encrypted-at-rest bytes only, not guaranteed plaintext" scoping caveat added to the design doc, at minimum, before any implementation decision.
- **`core` has zero dependency on `kinnector-config`** anywhere (same finding as Windows) — but the wiring *pattern* already exists and works: `antitheft-agent/src/trust_cache.rs:22` (`initialize_trust_cache(config: &kinnector_config::ConfigManager)`) already depends on `kinnector_config` and calls `config.system_package_paths()`. It just isn't pointed at a `protect-community/configs/antitheft/` domain (doesn't exist yet — only stale `configs/antithief/`, do not resurrect) or at any `ProtectedResource`/`PackageManagerContext` schema from §7 yet.
- **`warden_helper.cpp`** is an 8-line literal placeholder (`"Warden Helper Initialized (Placeholder)"`, returns true, does nothing) — name suggests Warden-specific, not clearly Antitheft-relevant; flagged for completeness, not prioritized below.
- **What consumes this today**: `antitheft-agent` (not `warden`) calls the sensitive-inode/trust-exec FFI surface directly, with extensive `#[cfg(unix)]` gating throughout. It is not thinner than the Windows side — if anything more built out — but per `antitheft.md`'s own explicit instruction, this is legacy pre-design code to reconcile file-by-file, not a head start to build on as-is (the `suspend_process_tree`/alerting shape confirms why).

## Testing strategy — the existing suite doesn't cover what matters most

**What exists today (verified by reading all of it, not just `test_lsm.cpp`/`test_ebpf_loader.cpp`)**: `CMakeLists.txt` registers 9 `ctest` targets — `test_ipc`, `test_lsm`, `test_telemetry`, `test_warden_helper`, `test_fanotify`, `test_ebpf_loader`, `test_linux_ipc`, `test_ffi`, `test_warden_all` (~1000 lines total, `test_warden_all` is an orchestrator that runs the others, not an independent test). All of them follow the same shape: mock-mode-vs-real-kernel-mode split, map CRUD returning true/false, loader lifecycle (`Initialize`/`Start`/`Stop`, double-call safety), FFI surface returning correct values before/after init. Useful, real, worth keeping.

**The gap that matters most: none of them assert actual enforcement.** Not one test in the entire suite issues a real `open()`, `write()`, `ptrace(PTRACE_ATTACH, ...)`, or `kill()` syscall from a distinct unprivileged process against a protected resource and checks that the kernel actually returned `-1`/`EACCES`/`EPERM`. Every existing test checks "did the map write succeed" or "is the loader in the state I expect," never "did the LSM hook's deny branch actually fire and block the syscall." That's the one thing every phase below (and Warden's own production behavior) actually depends on, and it's currently unverified by anything automated. A regression that flips a deny to an allow — or an allow to a deny on Warden's side, from a Phase 3/5 gating mistake — would not be caught by `ctest` today.

**No CI exists anywhere for `core/`** (confirmed — no workflow file references it; the only `.github` in the workspace is the org profile repo, unrelated). Every test here requires root + a kernel with BPF LSM enabled, so this was never going to be a normal hosted-CI target, but that makes a reliable local `ctest` run even more load-bearing as the only regression gate that exists.

**Required additions, layered onto the existing suite rather than replacing it:**

1. **A new `test_enforcement_e2e.cpp` ctest target — real syscalls, real deny checks.** `fork()`+`exec()` a small helper binary as a distinct process (not just call functions in-process — the LSM hooks key off the *calling* task, so the test must actually be a different process to mean anything), attempt `open()`/`write()`/`ptrace_attach`/`kill()` against a resource the test has pre-configured as protected via the existing FFI (`AddSensitiveInode`/`AddProtectedStaticInode`/the new `resource_owner_map`/`protected_owner_pids` from Phases 3/5), and assert the syscall's actual return value and `errno`. This becomes the base regression test every phase below extends — Phase 2 adds a PID-reuse case to it, Phase 3 adds the owner-allowlist case, Phase 5 adds the ptrace/kill case. Needs both a `MODE_ANTITHEFT` run and a `MODE_WARDEN` run of every case once the mode gate from the "Critical constraint" section exists, asserting the two modes produce different (correct-for-that-product) outcomes from the identical syscall attempt.
2. **Deterministic PID-reuse test for Phase 2**, not reliance on natural wraparound (too slow/nondeterministic to be a real regression gate): fork a process, let it exit, immediately fork a new one, and — since natural PID reuse isn't guaranteed on the next fork — either loop until the kernel actually reuses the PID or use `unshare(CLONE_NEWPID)` in a throwaway namespace to force low PID reuse deterministically. Assert the new process does not inherit the old one's `pid_tree_type_map`/lineage marker.
3. **BPF verifier regression check as its own automated step**, separate from behavioral correctness: `bpftool prog load` (or the loader's own `Initialize()` in real-kernel mode, which already fails loudly if the verifier rejects the object) after every phase that adds branches/map lookups to `file_open`/`file_permission` (Phases 3 and 5 both do). BPF programs have a hard instruction-count/complexity budget the verifier enforces — this is a real way a change can fail that has nothing to do with logic correctness, and nothing in the current suite catches it except incidentally (`test_lsm`'s `Start()` call would fail, but nothing asserts *why*). Confirm the built object still loads and attaches cleanly, not just that map operations against it succeed.
4. **A stress/load pass**, since `file_open`/`file_permission`/`ptrace_access_check`/`task_kill` run on every relevant syscall system-wide, on both a server (Warden) and a consumer machine (Antitheft): run a real workload (e.g. `stress-ng --fork`, a build, or a fork-bomb-shaped install-script simulation for Phase 1/2's install-context path specifically) with the LSM active and confirm no measurable latency regression and no crash/OOM in the eBPF ring-buffer/map-eviction path. This is the practical check for whether Phase 1's newly-attached `mmap_file`/`tracepoint_sched_process_fork` programs impose real overhead on Warden's servers, which the plan currently only asks to confirm functionally, not under load.
5. **Edge-case/negative matrix**, run against the Phase 3 owner-allowlist and Phase 6 canonical-identity work specifically: symlink and hardlink aliasing to a protected resource, a bind-mount exposing the same inode under a second path, two processes racing to open the same resource concurrently, the configured owner process crashing/restarting (does `resource_owner_map` go stale and either wrongly allow or wrongly deny the legitimate replacement process), and the TOCTOU window between a category/ownership lookup and the actual open completing.
6. **Extend `test_warden_all.cpp`'s orchestrated run** to include the new `test_enforcement_e2e` target's `MODE_WARDEN` cases, so "run wardend's own test/verification path" (referenced in the Critical constraint section and every phase's test criteria below) has a literal, single command behind it — `ctest` (or `ctest -R warden` for just the Warden-relevant subset) — rather than being a vague manual-smoke-test instruction.

None of this needs to be built before Phase 1 starts — item 1 (the e2e harness) is the one prerequisite worth building first, since Phases 2/3/5 each just add a case to it rather than inventing their own ad hoc test each time. Items 3 and 4 can be added once Phase 3 lands, since that's the first phase that actually grows the hot-path hook logic.

## Phase 1 — Activate the two dead BPF programs (near-zero risk, but still shared)

- Attach `tracepoint_sched_process_fork` in both `LoadAndAttachLsm()` and `LoadAndAttachFallback()` in `ebpf_loader.cpp`. This alone activates the already-written §4 propagation logic.
- Attach `mmap_file` the same way, for SO-sideload/module-load telemetry.
- These two programs are attach-point activations, not new Warden-facing branches — they were dead in both deployments, so activating them changes behavior for Warden too (fork-propagation of `pid_tree_type_map`/`process_threshold_map`/`trusted_ancestor_roots`/`admin_session_pids`, and new `mmap_file` telemetry volume, now happen on servers as well). Lower-risk than Phase 3/5 since it's pure activation of already-reviewed logic rather than new logic, but it's not risk-free for Warden — call this out explicitly when landing it, don't assume "dead code" means "Antitheft-only."
- **Test**: spawn a process descended from a package-manager binary, confirm `pid_tree_type_map`'s `TREE_INSTALL_CONTEXT` marker actually propagates to children now (it currently won't, since the copy-forward program isn't running). Separately, `dlopen` an executable mapping in a test process and confirm the corresponding telemetry event now arrives. **Also**: run `wardend`'s existing test/verification path (`test_lsm.cpp`, `test_ebpf_loader.cpp`) and a manual server-side smoke test to confirm no behavioral change or new overhead on the Warden side from these two programs now running.

## Phase 2 — Fix the PID-only key bug

- Change `pid_tree_type_map`'s declared key type from raw `uint32_t` to `struct process_key {pid, start_time}`, matching `process_threshold_map`/`trusted_ancestor_roots`. Touches the map declaration (`:238-243`), every read/write site (`bprm_creds_for_exec`, `ptrace_access_check`, `task_kill`, `sched_process_exit`, `sched_process_fork`), and the C++ `UpdateMapEntry`/`DeleteMapEntry` `PidTreeType` branch (`ebpf_loader.cpp:478-480, 535-536`).
- **Test**: spawn a process, kill it, spawn a new one that reuses the same PID (or force this deterministically), confirm the new process does *not* inherit the old one's install-context marker — the direct regression test for the bug being fixed, same shape as the Windows plan's equivalent test.

## Phase 3 — Real owner-allowlist enforcement (the load-bearing item)

- Add a new BPF map (e.g. `resource_owner_map`, keyed on protected inode → a small set/bitmask of trusted exec-inode-hashes representing the resource's legitimate owner processes) and check it in `file_open`/`file_permission` — **gated behind `mode == MODE_ANTITHEFT`** (see "Critical constraint" above) and appended after the existing trust-level check, not interleaved with it — comparing against the *accessing process's own* exec inode (already resolvable elsewhere in this same file via `bprm_file`).
- This is what actually delivers Antitheft's core promise on Linux ("refused before it completes," not "flagged after the fact"). Everything else in this doc is supporting infrastructure around this one change. It is also the phase with the largest blast radius if the mode-gate is done wrong, since `file_open`/`file_permission` are Warden's two busiest hook functions — do not skip the gating step to save time.
- **Test**: configure two processes as the only allowed owners of a tracked resource; confirm a third, unrelated process is denied at `open()` time (not merely logged afterward), and confirm both allowed owners can still read/write normally. **Also**: run the same scenario with `mode == MODE_WARDEN` and confirm `resource_owner_map` is never consulted and Warden's existing `file_open`/`file_permission` behavior is byte-for-byte unchanged; run `wardend`'s own test/verification path as a second confirmation.

## Phase 4 — Config-driven package-manager list

- Move `is_install_binary()`'s hardcoded string list to a userspace-populated map, mirroring `exec_allowlist_map`'s existing shape, sourced from `PackageManagerContext` (§7) via the same `kinnector_config`-wiring pattern `trust_cache.rs` already proves works.
- **Test**: add a new package-manager binary via config only (no rebuild), confirm it's recognized as an install-context root without a kernel-object rebuild.

## Phase 5 — Generalize owner-process protection beyond Warden/admin-session

- Extend `ptrace_access_check`/`task_kill`'s existing deny branches to also check a new `protected_owner_pids` map (keyed on `process_key`, populated when a process matches a configured owner binary pattern — same population pattern already used for `admin_session_pids`), **as an additional `or`-branch gated behind `mode == MODE_ANTITHEFT`**, so a configured credential-manager process gets the same ptrace/signal protection Warden's own binary and admin sessions already get, without changing what triggers protection in a Warden deployment.
- **Test**: run a tracked "owner" process (e.g. a stand-in for a password manager), confirm an unprivileged process is denied `ptrace_attach`/`SIGKILL` against it, and confirm the same denial did *not* previously apply before this change (regression baseline). **Also**: with `mode == MODE_WARDEN`, confirm `protected_owner_pids` is never consulted and the existing `TREE_ADMIN_SESSION`/`"warden"` comm-string protection behavior is unchanged.

## Phase 6 — Canonical identity composite key

- Add `(dev_t, inode)` to the sensitive/protected-inode identity resolution — both the kernel map keys and the userspace `stat()`-based population logic (which lives in `antitheft-agent`, not `core/`, and needs a paired change there).
- **Test**: create the same-inode-number condition across two different mounted filesystems (or a bind mount) and confirm no cross-filesystem misattribution occurs.

## Phase 7 — Scope the Secret Service / GNOME Keyring / KWallet gap

- This needs a design decision before implementation, not code first: document the same "encrypted-at-rest bytes only, not guaranteed plaintext" scoping caveat in `antitheft.md` that Windows' DPAPI gap already has, and decide whether D-Bus method-call interception (`Secret.Service.Unlock`/`OpenSession`) is in scope for a later phase or stays explicit residual risk.
- No test criteria yet — this phase's output is a design decision + doc update, not code.

## Phase 8 — `fanotify.cpp` blocking mode (lower priority)

- Switch to `FAN_CLASS_PRE_CONTENT`/`FAN_CLASS_CONTENT` init and add `FAN_OPEN_PERM`/`FAN_ACCESS_PERM` marks plus the currently-entirely-absent allow/deny response write-back loop, as a belt-and-suspenders fallback for kernels without BPF LSM support — mirroring the fallback-tracepoint split `EbpfLoader` already has.
- **Test**: on a kernel with BPF LSM disabled (or force fallback mode), confirm fanotify-based blocking still denies access to a protected resource.

## Cross-cutting note

Every phase above needs a paired change in `antitheft-agent` (or the future unified `antitheftd`, see `antitheft.md` §2/§8 — no OSS/Pro split for this product) to actually consume/configure the new kernel behavior — same principle as the Windows plan's cross-cutting note. Additionally: the legacy `heuristics.rs` owner-check logic (`suspend_process_tree`/`wall` broadcast shape) should be explicitly retired once Phase 3 lands, not left running in parallel with a real kernel-side deny — running both means either double-alerting on the same event or the legacy path silently no-oping once the read it was watching for no longer happens.

Every phase's "Test" bullet references the ctest suite — see the "Testing strategy" section above for what that concretely means (which target, what it actually needs to assert, and why the existing suite alone isn't enough). Build the `test_enforcement_e2e` harness before or alongside Phase 1, not after Phase 3 — retrofitting real syscall-level assertions onto a suite that's already shipped several phases of shared-hook changes is a much worse position to debug from.
