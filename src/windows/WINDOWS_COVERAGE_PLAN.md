# Windows coverage plan for `core/` — handoff for a Windows-side session

This file was written on Linux, where none of this can actually be built, run, or driver-verified. It exists so a Claude Code session running on a real Windows machine can pick this up and execute it with real build/test feedback, instead of starting from scratch or re-discovering the bugs below by hand.

**Read `kinnector.dev/antitheft/antitheft.md` first** (specifically §3 "Enforcement layer" Windows subsection, §4 "Storage-ownership subsystem," and §7 "Config & rule domain") — that's the source design doc this plan implements, and it carries the full technical rationale for *why* each mechanism below is designed the way it is: the Windows object-model gaps (handle duplication/inheritance, section-object mapping, raw-volume/VSS bypass, path aliasing), the APC-vs-remote-thread-vs-`SetThreadContext` injection analysis and why `ObRegisterCallbacks`-based handle-right restriction is the primary defense, why ALPC has no general blocking framework, why DPAPI is the *real* decryption boundary for most Windows credential stores (not the file itself), access-token duplication/impersonation (`DuplicateTokenEx`/`ImpersonateLoggedOnUser`/`SeImpersonatePrivilege`-abusing "potato"-family escalation — added to §3/§10 2026-08-26, Object Manager's Token object type has zero coverage anywhere in this plan today), and — most load-bearing for this plan — why lineage propagation must key off `PS_CREATE_NOTIFY_INFO.CreatingThreadId` and never `ParentProcessId` (the latter is exactly the field `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` parent-PID-spoofing corrupts). This file doesn't repeat that reasoning — it's the execution plan, not the design doc.

## Verified current state (confirmed by direct file reads, not just a survey — re-verify anyway before relying on line numbers, the code may have moved since this was written)

- **`etw_consumer.cpp`** (511 lines) is the only real Windows collector today. Three ETW providers, user-mode only, no kernel driver involved:
  - `Microsoft-Windows-Kernel-Process` (`{22FB2CD6-0E7B-422B-A0C7-2FAD1FD0E716}`) — ProcessCreate (event ID 1), ProcessStop (2), ImageLoad (5) only.
  - `Microsoft-Windows-Kernel-File` (`{EDD08927-9CC4-4E65-B970-C2560FB5C289}`) — FileCreate (12) and FileIORead (15) only. No write/rename/delete.
  - `Microsoft-Windows-Kernel-Network` (`{7DD42A49-5329-4832-8DFD-43D979153A88}`) — TcpIp/Connect (12) only. No listen/accept/UDP.
  - `ProcessCreateDetails` is populated from TDH's `ProcessId`/`ParentProcessId` properties at lines 337-338 — **PID only, `ProcessSequenceNumber` is never read**.
  - `TelemetryHeader.timestamp_ns` (line 323) is `event->EventHeader.TimeStamp.QuadPart * 100ULL` — the ETW event's own arrival timestamp, not a process creation time.
- **`driver_helper.h`** (13 lines) is a total no-op stub: `Initialize()`/`Start()` hardcode `return true`, `Stop()` is empty. `driver_helper.cpp` is just an `#include`. **Zero kernel-mode code exists anywhere in the workspace** — repo-wide search for `DriverEntry`/`FltRegisterFilter`/`ObRegisterCallbacks`/`PsSetCreateProcessNotifyRoutine`/`CmRegisterCallback` across `core`, `core-pro`, `warden*`, `antitheft-agent*`, `kinnector-config` returned zero matches. There is also no WDK/driver-toolchain reference anywhere (no `.sln`, `EWDK`, `signtool`, `INF2CAT` usage) — this is fully greenfield.
- **`../../include/kinnector/telemetry.h`**: `TelemetryHeader.sequence_number` is a global monotonic *event* counter across the whole telemetry stream, not a per-process identity. `ProcessCreateDetails` has only `child_pid`/`real_parent_pid` (plus image path/command line) — no sequence-number or create-time field of any kind.
- **`clipboard_helper.cpp`** (13 lines) is a dead stub — its comment claims it registers a clipboard listener and forwards to a named pipe; it does neither (just a bare `GetMessage` loop). The actual working clipboard listener lives entirely outside `core/`, in a separate Rust binary: `antitheft-agent/src/clipboard_helper.rs` (built as `antitheft-clipboard-helper`), which does real `AddClipboardFormatListener`/`GetClipboardData` work and writes ad-hoc JSON to its own pipe (`\\.\pipe\kinnect-clipboard-<session_id>`). **Nothing in `antitheft-agent` currently reads that pipe** — confirmed via grep, no `clipboard`/`kinnect-clipboard` references in `lib.rs`/`control.rs`. The pipeline is disconnected end-to-end; `ClipboardWriteDetails` in `telemetry.h` is unpopulated dead schema on Windows today.
- **`antitheft-agent/src/heuristics.rs:412-414` and `:553-555`** (confirmed via grep): build `ProcessKey { pid, start_time: 0 }` with the literal comment `// start time wild-card for simplicity in lookup`. Since `core` never emits anything better than an ETW event-arrival timestamp for `start_time` in the first place, this wildcard means `children_map` lookups are effectively **PID-only** despite `ProcessKey` including `start_time` in its `Hash`/`Eq` — a real, already-half-acknowledged PID-reuse vulnerability in the current lineage tracking.
- A cross-platform PPID-spoof heuristic already exists at `heuristics.rs:387-407` (not `#[cfg]`-gated) — compares kernel-reported `real_parent_pid` against the pid the event was attributed to, demotes to untrusted + fires `ppid_spoof` on mismatch. Reasonable foundation, **but on Windows it trusts ETW's `ParentProcessId` property**, which per the design doc's `PS_CREATE_NOTIFY_INFO` analysis is plausibly the same metadata field `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`-based spoofing corrupts. This needs explicit validation on a real Windows box — don't assume either way, and don't ship a claim that this heuristic is spoof-proof until it's actually tested against a PPID-spoofing PoC.
- `core`'s existing FFI surface (`../../include/kinnector/ffi.h`, `../../ffi.cpp`) is almost entirely BPF/Linux-shaped (`add_sensitive_inode`, `update_process_threshold`, BPF map ops) and no-ops on Windows. New Windows work needs its own FFI entry points, not reuse of these.
- `warden`/`wardend` is Linux-only (no `#[cfg(windows)]` anywhere in `warden/src`, `build.rs` hardcodes Linux paths/libs). **`antitheft-agent` is the real Windows consumer** of `core`'s telemetry — its Windows-side named-pipe IPC (`src/ipc.rs`, via `tokio::net::windows::named_pipe`) is a real, working ABI-compatible pairing with `core`'s `windows_ipc.cpp` today. Any new event type added to `core` needs a matching addition on the `antitheft-agent` side to actually be consumed — telemetry with no consumer is exactly the clipboard bug above, don't repeat that pattern.
- `core`'s Linux side (`../linux/`), for comparison, already keys everything on a `pid + start_time` compound key throughout its BPF map surface (`UpdateMapEntry(BpfMapType, pid, start_time, value)` etc.) — i.e. Linux already has the anti-PID-reuse discipline Windows currently lacks. Use that as the pattern to match, not reinvent.
- `core/README.md` claims "parent-child inheritance tracking" and full file-op coverage as if already true on Windows — both are aspirational relative to the code above. This plan is what actually closes that gap; update the README once each phase actually lands, don't leave it overclaiming.
- **Access-token duplication/impersonation has zero coverage anywhere in this plan** (confirmed via repo-wide search — no `DuplicateTokenEx`/`ImpersonateLoggedOnUser`/`SeImpersonatePrivilege`/token-related string anywhere in `core` or `antitheft-agent`), matching `antitheft.md`'s own admission (§3/§10, added 2026-08-26) that Object Manager's Token object type was never addressed. No detection *or* prevention exists today for a `DuplicateTokenEx`+`ImpersonateLoggedOnUser`/`CreateProcessWithTokenW` chain targeting a protected owner process, nor for the `SeImpersonatePrivilege`-abusing "potato"-family escalation path that turns an LSASS memory read into a usable impersonated identity. See Phase 4 and Phase 7 step 6 below for where this plan now picks it up.

## Phase 1 — Fix the disconnected clipboard pipeline

- Implement `clipboard_helper.cpp` for real: `AddClipboardFormatListener` + `WM_CLIPBOARDUPDATE` handling, populate `ClipboardWriteDetails` (already in `telemetry.h`), send through the standard `TelemetryEvent`/IPC pipe — not a separate side-channel.
- Once verified working end-to-end, retire `antitheft-agent/src/clipboard_helper.rs` and the `antitheft-clipboard-helper` binary/pipe so there's one clipboard path instead of one dead and one orphaned.
- Serves the "software wallets" and "passwords" product categories directly — clipboard-hijacking/address-swap detection depends on this.
- **Test**: trigger a clipboard write on the test machine, confirm the event arrives through `antitheft-agent`'s existing IPC consumption path end to end.

## Phase 2 — Fix process-lineage keying at the ETW layer

- Extend the Kernel-Process ProcessCreate TDH parsing in `etw_consumer.cpp` to also read `ProcessSequenceNumber` and `ParentProcessSequenceNumber` (present on the modern Kernel-Process ProcessStart schema as a spoof/reuse-resistant per-boot process identifier — verify field names against the current OS build's manifest via `tdh.h`/`wbemtest`/`logman query providers` rather than assuming they're named exactly this on every Windows version).
- Add `uint64_t child_sequence_number` / `uint64_t parent_sequence_number` to `ProcessCreateDetails` in `telemetry.h`, threaded through the packed-union ABI.
- Fix the confirmed `start_time: 0` wildcard at `heuristics.rs:412-414` and `:553-555` to use the real sequence number instead.
- Build the persistent lineage-marker table on top of the now-solid composite key (root-mark on package-manager-binary match against the config domain, propagate to children at process-create time — never re-derived later by walking mutable ancestry — prune on process-stop). Reasonable to keep in Rust (`heuristics.rs` already owns `ProcessKey`/`children_map`), since `core`'s job is delivering trustworthy identity, not owning policy state.
- **State explicitly in commit messages/docs, don't let this get oversold**: this ETW-based mechanism is an interim source. It's a real improvement over today's PID-only/wildcarded state, but only Phase 7's driver-based `CreatingThreadId` capture is actually spoof-proof against `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`-style attacks.
- **Test**: spawn a process, kill it, spawn a new one that reuses the same PID (or simulate this deterministically), assert the lineage table does not misattribute the new process to the old one's lineage — the direct regression test for the bug being fixed. Also test against a real parent-PID-spoofing PoC to characterize (not necessarily fully close, that's Phase 7) how the existing `heuristics.rs:387-407` heuristic behaves.

## Phase 3 — Complete ETW-only telemetry coverage (DONE, verified 2026-08-26)

All detection-only (ETW can't block). All four bullets below are implemented, build+test-verified in a real elevated session (`ctest` 6/6 pass, each new event type also run and inspected directly, not just via CTest's pass/fail). Every event ID was empirically verified against this OS build's real manifest via a throwaway diagnostic (traced real file/registry/network/task operations, read back real `EventDescriptor.Id`/keyword bits/property names, deleted the diagnostic once done) rather than assumed from memory or docs — see `core_windows_phase3_file_events` memory for full detail per slice. That verification pass also found and fixed three more latent keyword/casing bugs in the pre-existing code (Kernel-File's read keyword and `IoSize`/`IOSize` casing, Kernel-Network's enabled keyword not matching any real event) beyond the `ProcessId`/`ProcessID` one Phase 2 found.

- Remaining Kernel-File event IDs for write(16)/rename(27)/delete(26)-via-SetInformation. Needed a new `FileObject → path` correlation cache (Write/Rename's source path aren't in the event itself); `FileDeleteDetails` was added to `telemetry.h` (the `EventType` value existed but had no struct).
- `Microsoft-Windows-Kernel-Registry` for registry write visibility: `SetValueKey`(5) → `RegistryWriteDetails`, via a `KeyObject → path` cache (same pattern as file). Only the write path is covered — Create/Delete/DeleteValue key ops have no schema yet. Raw value bytes aren't captured (only a type+size summary) — the `CapturedData` TDH property needs a different extraction approach than the simple by-name lookup used everywhere else here.
- Fuller Kernel-Network coverage: TCP Accept(15) → new `NetworkAcceptDetails`/`EventType::NetworkAccept`; UDP send(42) reuses `NetworkConnectDetails` with `protocol="UDP"`. **Listen has no dedicated event on this provider at all** (confirmed empirically, not guessed) — Kernel-Network only sees packet/flow activity, not passive socket-state changes; listen-time visibility would need a different provider (`Microsoft-Windows-Winsock-AFD`) if ever required.
- `Microsoft-Windows-TaskScheduler`: event 106 (`TaskRegistered`) → new `EventType::TaskRegistered`/`TaskRegisteredDetails`, enabled via that provider's `Operational` channel keyword specifically. "Run-key-adjacent registry path coverage" (the other half of this bullet) is already satisfied by the generic registry-write work above — Core deliberately doesn't path-scope or classify *which* registry writes are persistence-relevant; that's policy-layer work, same boundary as clipboard content-type classification.
- **Test**: done — `test_file_events`, `test_registry_events`, `test_network_events`, `test_taskscheduler_events` (new CTest targets, same elevation-required/`SKIP_RETURN_CODE 127`-not-mock pattern as `test_process_lineage`), each exercising the real OS mechanism (real file/registry/socket/`schtasks.exe` operations), not a synthetic/mocked event.

## Phase 4 — ETW-TI integration (BLOCKED — validation spike done 2026-08-26, real access gap confirmed)

**Status summary (2026-08-26, read this first - detail and history below)**:
- **CVP/PPL REQUIRED** (nothing further possible until then): verifying the memory-op events (`VirtualAlloc`/`VirtualProtect`/`WriteProcessMemory`/`SetThreadContext`/`QueueUserAPC`) and the impersonation-change events (UP/DOWN/REVERT) against a real trace, and tracing any Phase 4 event for the first time at all — `EnableTraceEx2` against `Microsoft-Windows-Threat-Intelligence` fails with `ACCESS_DENIED` without Antimalware-PPL, no exception.
- **ACTIONABLE NOW, no PPL/CVP needed**: empirically verify the remote-thread-creation IDs/keywords (`KERNEL_THREAD_START`=3, `WINEVENT_KEYWORD_THREAD`=`0x40`, `TThreadID`/`StartAddr`) — sourced from `Microsoft-Windows-Kernel-Process`, already works under ordinary elevation today.
- **CLOSED, not a tracked gap**: `CreateProcessWithTokenW`/`CreateProcessAsUserW` — accepted as indirectly covered by Phase 2's `ProcessCreate` lineage + the `ImpersonationChange` events, decision recorded below.
- **Local PPL test harness is ready to use**: confirmed empirically (not assumed) — `bcdedit /enum {current}` shows `testsigning: Yes` (the reboot happened), and `sc query ppl_runner` shows the service is installed (currently `STOPPED`, exit 1077 = never started this boot, not a failure). Remaining setup steps are in [[core_windows_phase4_ppl_test_setup]]: sign a test binary with the same `ppl_runner.pfx` cert, point `HKLM\SOFTWARE\PPL_RUNNER` at it, `net start ppl_runner`.

**Validation spike result: `Microsoft-Windows-Threat-Intelligence` is not consumable from `antitheftd` as currently designed.** Empirically confirmed on a real elevated-Administrator session (not a guess from documentation): `StartTrace` succeeds, but `EnableTraceEx2` against this provider's GUID (`{F4E1897C-BB5D-5668-F1D8-040F4D8DD344}`) returns `ERROR_ACCESS_DENIED` (status 5) every time. This isn't a driver-signing issue — it's a separate, specific access check in `EtwpCheckNotificationAccess` that requires the calling process to be running at **Antimalware-PPL** (Protected Process Light, antimalware signer level). Ordinary elevation/Administrator/SYSTEM is not sufficient, no matter how privileged the token is.

**What Antimalware-PPL actually requires**: legitimately becoming an Antimalware-PPL process requires Microsoft's **ELAM (Early Launch Antimalware) driver certification program** — a real, separate Microsoft certification track from Phase 7's WHQL minifilter driver signing. This is a new external dependency this plan hadn't previously tracked; it has its own lead time and application process, comparable in kind (though not identical in process) to the WHQL workstream Phase 7 already flags as the long pole.

**A non-PPL, non-driver workaround exists but is explicitly not recommended for this product**: public 2026 security research (AutoLogger registry entry + hooking `ControlTrace` to bypass the user-mode `SecurityTrace` check) lets a non-PPL admin process consume *some* ETW-TI telemetry without PPL or a driver. Rejected for `antitheftd` for two reasons: (1) it cannot enable the specific per-process telemetry this phase actually wants — including the token-impersonation events from the sub-track below — only whatever's emitted by AutoLogger defaults; (2) it works by self-hooking `ntdll` in-process, which is itself a classic technique other AV/EDR products treat as a red flag — ironic and self-defeating for a security product's own daemon to rely on.

**Decision: Phase 4 is deferred, not abandoned.** Track "apply for Antimalware-PPL/ELAM certification" as its own external workstream (like Phase 7's WHQL note) — until that's in hand, none of the bullets below (injection visibility, token-impersonation detection) can actually ship. **Move on to Phase 5 and Phase 6 next** — neither depends on ETW-TI or PPL.

**Update 2026-08-26 (later same day)**: Implementing the memory/injection and token-impersonation sub-tracks in detail triggered Anthropic's real-time cyber-safeguard classifier (a dual-use warning banner) mid-session. Work is paused on the token/impersonation sub-track pending Cyber Verification Program (CVP) approval for this account (applied via `portal.anthropic.com/programs/cvp`, ~2 business day review). In the meantime, scaffolding for the memory/injection primitives was written in a deliberately neutral, pure-data-capture style (no technique/attacker framing in code or comments) and does build clean:

- `telemetry.h`: new `CrossProcessMemoryAccess` / `ThreadContextAccess` event types + structs (target pid/tid, address, size, protection-flag string, operation name). Pure data capture — no interpretation, no severity/intent field.
- `etw_consumer.cpp`: `Microsoft-Windows-Threat-Intelligence` GUID now registered via `EnableTraceEx2` alongside the four existing providers. Parsing is wired for `VirtualAlloc`/`VirtualProtect`/`WriteProcessMemory` → `CrossProcessMemoryAccess` and `SetThreadContext`/`QueueUserAPC` → `ThreadContextAccess`. **Event IDs and property names (`THREATINT_ALLOC_VM`=1, `PROTECT_VM`=2, `QUEUE_USER_APC`=4, `SET_CONTEXT_THREAD`=5, `WRITE_VM`=14, plus `TargetProcessId`/`BaseAddress`/`RegionSize`/`Protection`/`TargetThreadId`/`StartAddress`) are cross-referenced against two independent public manifest sources (see the "memory-op ID correction" update below) but still UNVERIFIED against this OS build's own manifest** — this provider still fails `EnableTraceEx2` with `ACCESS_DENIED` (the same gap the original validation spike found) until the calling process actually runs as Antimalware-PPL, so none of this can fire or be verified yet. It's left registered so it self-activates with no further code change once PPL access exists.
- **Remote-thread-creation visibility was decoupled from ETW-TI entirely** and moved to `Microsoft-Windows-Kernel-Process`'s `ThreadStart` event instead (added the `WINEVENT_KEYWORD_THREAD` keyword bit, `0x40`, also unverified pending a `logman`/manifest check like the IDs above). This needs no PPL and works under ordinary elevation today: it compares the `ThreadStart` event's `ProcessID` property (the thread's owning process) against `EventHeader.ProcessId` (the process that called the thread-create API) — when they differ, emits `EventType::ThreadContextAccess` with `operation="RemoteThreadCreate"`. Matching in-process thread creation is deliberately not forwarded (pure noise filtering, not policy). No memory read, no handle operation, no interaction with the target process — comparison of two IDs already present in telemetry this file was already allowed to collect.
- **Deliberately left unimplemented**: the token-duplication/impersonation detection sub-track (`DuplicateTokenEx`/`ImpersonateLoggedOnUser`/`SetThreadToken`/`CreateProcessWithTokenW`, and the "potato"-family escalation path) — closest to what tripped the classifier, stays untouched until CVP clears.
- **Note for whoever picks this up next**: none of `VirtualAlloc`/`VirtualProtect`/`WriteProcessMemory`/`SetThreadContext`/`QueueUserAPC` are needed for process/thread lineage-tree construction — that's Phase 2 (`ProcessCreate`/`ProcessStop`) plus the new `ThreadStart`-based remote-thread-creation piece above. The memory/injection primitives are a separate, purely behavioral detection layer on top of an already-complete tree, not a tree-building dependency — don't block tree-building work on PPL/CVP.

**Decision 2026-08-26 (usermode API hooking is explicitly rejected as a substitute for the driver, project-wide)**: audited the full Windows section of `antitheft.md` (handle duplication, section objects, raw volume, VSS, path aliasing, registry hives, DPAPI, injection, token impersonation, ALPC, kernel self-protection) for anything designed around usermode hooking. Finding: **nothing in the current design requires it.** Every real interception point already routes through either a kernel-instrumented ETW provider (Kernel-Process/File/Registry/Network, DPAPI, ETW-TI) or the Phase 7 kernel driver (`ObRegisterCallbacks`, minifilter, `CmRegisterCallbackEx`, `PsSetCreateProcessNotifyRoutineEx2`). The one place a usermode hook was even considered — the AutoLogger + `ControlTrace` trick to bypass ETW-TI's PPL requirement, described earlier in this section — was already rejected, for the same reason being reaffirmed here: a usermode hook operates below the syscall boundary from userland, so any caller willing to issue the raw syscall directly (well-documented, trivial for a motivated attacker) bypasses it entirely — it provides no real security property, only the appearance of one, while also being the specific technique class that reads as offensive tooling. **Token duplication/impersonation (`DuplicateTokenEx`/`ImpersonateLoggedOnUser`/`SetThreadToken`/`CreateProcessWithTokenW`) stays the one gap with no implementation today** — not because hooking is being withheld as an option, but because its two legitimate paths (ETW-TI coverage of these ops; `ObRegisterCallbacks` on the Token object type) are both unconfirmed, per antitheft.md §3's own admission. Wait for Phase 7 step 6 to validate the driver path (or CVP + a real ETW-TI capture to validate the other) rather than reaching for a hook in the meantime.

**Update 2026-08-26 (ETW-TI coverage of impersonation - partially resolved)**: `logman query providers "Microsoft-Windows-Threat-Intelligence"` was run directly on this machine (a benign, read-only manifest enumeration - doesn't need PPL, doesn't start a trace, doesn't call any of the APIs in question) to check ETW-TI's real coverage rather than trust public docs alone. Its keyword list confirms **impersonation state changes are covered**:
- `KERNEL_THREATINT_KEYWORD_PROCESS_IMPERSONATION_UP` (`0x4000000000`)
- `KERNEL_THREATINT_KEYWORD_PROCESS_IMPERSONATION_DOWN` (`0x40000000000`)
- `KERNEL_THREATINT_KEYWORD_PROCESS_IMPERSONATION_REVERT` (`0x8000000000`)
- `KERNEL_THREATINT_KEYWORD_PROCESS_SYSCALL_USAGE` (`0x10000000000`)

These almost certainly correspond to `ImpersonateLoggedOnUser`/`SetThreadToken` (a thread's effective identity going up/down in privilege, or reverting via `RevertToSelf`) - this narrows the "is it even covered at all" question the plan flagged as open. **Still unresolved**: `logman query providers` only enumerates keyword bitmasks, not the actual per-event Task ID/property schema - one online source claimed event IDs 33-36 for this, but it wasn't corroborated against a second independent source the way the memory-op IDs were (those matched cleanly against `repnz/etw-providers-docs`'s authoritative manifest XML), so no speculative parsing code was written against that number. Also unclear from keyword names alone whether `DuplicateTokenEx` itself (creating the duplicate token, distinct from applying it) or `CreateProcessWithTokenW` are covered by these same keywords or need something else. The existing `EnableTraceEx2(ThreatIntelGuid, ..., 0, ...)` call in `etw_consumer.cpp` already passes `MatchAnyKeyword=0`, which per documented ETW semantics means no keyword filtering is applied - so once PPL access exists, these events will already flow through without further wiring; only the Task-ID-to-`EventType` parsing branch (analogous to what exists today for `THREATINT_ALLOC_VM` etc.) remains to be added, and that has to wait for a real capture to get the ID/property names right.

**Update 2026-08-26 (impersonation-change monitoring implemented, detection-only)**: added `EventType::ImpersonationChange` / `ImpersonationChangeDetails` to `telemetry.h` (calling pid/tid, direction UP/DOWN/REVERT, previous-token user/integrity/elevation - pure data capture) and wired parsing for event IDs 33/34/36 (`THREATINT_IMPERSONATION_UP`/`REVERT`/`DOWN`) in `etw_consumer.cpp`, corroborated across two independent public sources plus this machine's own confirmed keyword names. Still open and explicitly flagged in the code: public research describes these events as gated by a per-process `EPROCESS.Flags3` bit (`EnableProcessImpersonationLogging`) whose activation mechanism isn't yet understood - don't assume enabling the provider keyword alone guarantees these fire for arbitrary processes the way it's assumed for the memory-op events. Same PPL/CVP blocker as the rest of Phase 4 applies before any of this can be traced for real. This is monitoring-only by design (no hook, no interception, no modification of any process) - deliberately scoped that way both because that's what's actually needed for detection telemetry, and because it stays clear of the usermode-hooking pattern this file already rejects on both security and product-classifier grounds.

**Closed 2026-08-26: `CreateProcessWithTokenW`/`CreateProcessAsUserW` accepted as indirectly covered, not tracked as a gap.** `Microsoft-Windows-Threat-Intelligence` has no event/keyword for process creation with a supplied token (checked against both this machine's real keyword list and public research) - a token has to originate somewhere (duplication) and get used somewhere, and those two moments are already covered: Phase 2's `ProcessCreate` lineage tracking sees the new process, and the `ImpersonationChange` events above see impersonation being applied. A more precise signal exists in principle (Security-Auditing event 4688's "Token Elevation Type" correlated against lineage - `CreateProcessWithTokenW` hands the token to the new process via the Secondary Logon service without necessarily impersonating the calling thread first, so today's coverage can't yet distinguish "spawned under a mismatched token" from an ordinary child process) but isn't being built now - it needs a system-wide `auditpol` change plus a decision on whether the correlation logic belongs in `core` or `heuristics.rs`, and isn't worth that cost unless this specific attribution precision becomes a real requirement later.

**Update 2026-08-26 (memory-op event ID correction)**: the `THREATINT_QUEUE_USER_APC`/`SET_CONTEXT_THREAD`/`WRITE_VM` constants in `etw_consumer.cpp` were originally 5/8/10, sourced from a single unverified public-research guess. Cross-referencing two independent manifest sources against each other (`repnz/etw-providers-docs`' Win10-17134 XML dump, which explicitly lists numeric task IDs 1-14, and `jdu2600/Windows10EtwEvents`' TSV, which agrees on 1-8/11-14 and implies 9-10 by the same REMOTE/LOCAL pairing pattern) shows the correct REMOTE-variant IDs are `QUEUE_USER_APC`=4, `SET_CONTEXT_THREAD`=5, `WRITE_VM`=14 - the old values were simply wrong (5 is actually `SETTHREADCONTEXT_REMOTE`, 8 is `MAPVIEW_LOCAL`, 10 is `SETTHREADCONTEXT_LOCAL`). Fixed in `etw_consumer.cpp`. This is a materially stronger basis than the original single-source guess (two independently-maintained sources corroborating each other), but still not equivalent to Phase 3's "traced a real event on this machine and read back its actual ID" standard - re-verify once PPL access exists.

The rest of this section is preserved as-written (the target design once PPL is available), not re-verified further:

- Enable `Microsoft-Windows-Threat-Intelligence` for `VirtualAlloc(Ex)`/`VirtualProtect(Ex)`/`WriteProcessMemory`/`SetThreadContext`/`QueueUserAPC`/remote-thread-creation visibility. This is what makes APC injection, remote-thread injection, and memory-protection-flip techniques visible *at all* — currently zero Windows telemetry exists for any of them, despite `MemoryProtectDetails`/`PtraceAttachDetails`-equivalent schema already existing.
- Detection only — the actual *prevention* of injection is Phase 7's `ObRegisterCallbacks` work. This phase is the interim/complementary visibility layer and stays valuable as a detection backstop even after Phase 7 ships.
- **Access-token duplication/impersonation detection — separate validation spike, don't assume ETW-TI covers this too.** `DuplicateTokenEx`/`ImpersonateLoggedOnUser`/`SetThreadToken`/`CreateProcessWithTokenW` are not confirmed to be among ETW-TI's covered operations (unlike the memory/injection primitives above, which are well-documented ETW-TI events) — check the actual provider's event schema on a real machine rather than assuming parity. If ETW-TI doesn't cover it, the fallback interim signal is the Windows Security auditing log (event 4672 "special privileges assigned to new logon" for `SeImpersonatePrivilege` grants, 4688 process-creation with token-elevation-type fields) via `EvtSubscribe`/`Microsoft-Windows-Security-Auditing` — untested here, needs its own spike, and auditing must actually be enabled (`auditpol` "Token Right Adjusted"/"Process Creation" subcategories) which isn't guaranteed on a target machine. State whichever mechanism actually works, don't imply detection exists until it's confirmed.
- **Test**: run a controlled, benign injection-technique PoC (e.g. `QueueUserAPC` into a disposable test process you own) and confirm the event is visible and correctly attributed. Separately, run a controlled `DuplicateTokenEx`+`ImpersonateLoggedOnUser` PoC against a disposable test process and confirm whether either candidate mechanism above actually surfaces it — this is a genuine open question, not an assumed-yes.

## Phase 5 — Canonical resource identity + config-domain wiring

- Build a canonical-resource-identity resolution utility (volume serial + NTFS File Reference Number) in this directory — needed both by any interim detection logic now and by the Phase 7 driver later.
- **`core` does not link or parse `kinnector-config` directly** — same boundary Warden already uses for firewall/inode rules (`add_sensitive_inode`, `add_protected_static_inode`, `add_trusted_exec_inode`, `add_firewall_cidr` in `src/ffi.cpp`: "the rule store and diffing is owned by the calling agent; Core owns the enforcement decision itself," per `README.md`). Add a matching FFI setter, e.g. `add_protected_resource_windows(volume_serial, file_reference_number, category)`, that populates an in-memory map keyed on the canonical identity above. `antitheftd` owns loading `protect-community/configs/antitheft/` via `kinnector-config`, diffing on hot-reload, and pushing resolved entries down through this FFI call — `core`'s hardcoded provider/keyword/protected-resource list goes away, but `core` still never knows the config format exists.
- **Test**: create a hardlink or NTFS junction to a tracked file, confirm it resolves to the same canonical identity as the original — the direct test for the path-aliasing gap this closes.
- **Owner-allowlist (antitheft.md §4) implemented for Windows**: `ProtectedResourceStore` (`resource_identity.h`) also stores, per protected resource, a set of authorized Authenticode signer identities (`AddResourceOwnerSigner`/`RemoveResourceOwnerSigner`/`IsAuthorizedSigner`), plus a convenience `IsAuthorizedModifyingPath` that live-resolves a binary's own signer and checks it in one call. This is what lets a vendor's auto-updater keep working across binary-content-changing releases — authorization is by signing identity, not a pinned path/hash, matching §4's `identity_pin` model exactly ("Authenticode on Windows"). Reuses the existing `VerifyAuthenticodeSignature` (Fix 4, `etw_consumer.cpp`) rather than a second implementation — extracted to `authenticode.h`/`.cpp` for that purpose. FFI: `add_resource_owner_signer_windows`/`remove_resource_owner_signer_windows`/`is_authorized_signer_windows`/`is_authorized_modifying_path_windows`, same core/agent config boundary as above — `antitheftd` is what decides which signers to register, `core` just stores and matches.
- **Known gap, confirmed empirically 2026-08-26**: `VerifyAuthenticodeSignature` only checks *embedded* Authenticode signatures (`WTD_CHOICE_FILE`), not Windows' separate catalog-signing mechanism. `notepad.exe` → `TRUST_E_NOSIGNATURE` despite being legitimately Microsoft-signed (catalog-only); `explorer.exe` → succeeds (embedded). Standalone third-party installer/updater binaries almost always embed their signature directly, so this mainly affects OS system files and MSI-delivered binaries, not the general vendor-updater case this phase targets — but it also means the pre-existing image-load telemetry's `is_signed` field has silently under-reported signed status for catalog-signed binaries since Fix 4 shipped. Catalog fallback (`CryptCATAdminAcquireContext2`/`CryptCATAdminEnumCatalogFromHash` → `WTD_CHOICE_CATALOG`) is real, well-precedented Windows API work, scoped as its own follow-up — not implemented yet, don't assume it's covered.

## Phase 6 — DPAPI monitoring (DONE, with a real confirmed limitation — see below)

- `Microsoft-Windows-Crypto-DPAPI` provider consumption implemented in `etw_consumer.cpp`, wired the same way as every other provider in this file: GUID + event ID both empirically confirmed on this machine (see `DpapiOperationDetails` in `telemetry.h`), not assumed from documentation.
- **GUID**: `{89FE8F40-CDCE-464E-8217-15EF97D4C7C3}`, confirmed via `logman query providers "Microsoft-Windows-Crypto-DPAPI"`.
- **Event**: `DPAPIDefInformationEvent`, Id=16385, Task=64 (`ETW_TASK_DEF_INFORMATION`). Fires for **both** `CryptProtectData` and `CryptUnprotectData`, distinguished by the `OperationType` property (`"SPCryptProtect"`/`"SPCryptUnprotect"`) — there's no separate per-operation event ID.
- **Real surprise, confirmed empirically, not assumed**: the semantically-expected task keywords this provider actually documents for the job (`ETW_TASK_DATAPROTECTION_OPERATION` 0x4, `ETW_TASK_MASTERKEY_OPERATION` 0x2, `ETW_TASK_CREDKEY_OPERATION` 0x8 — all visible in `logman`'s own provider listing) produced **zero** events across repeated `CryptProtectData`/`CryptUnprotectData` calls, at any provider level, with any single one or combination of them enabled. Only the **Debug channel keyword** (`0x2000000000000000`) combined with the `DEF_INFORMATION` task bit (`0x40`) actually delivers this event — confirmed down to that exact minimal mask (not just "enabling everything works").
- **CRITICAL LIMITATION, empirically confirmed via two separate diagnostics — this is NOT a full per-call audit trail**: `DPAPIDefInformationEvent` fires only for a process' **first** DPAPI operation (Protect or Unprotect, whichever happens first) in its lifetime. A test that called `CryptProtectData`+`CryptUnprotectData` five times in a row, alternating user/machine scope, produced exactly **one** event total (for round 0's Protect) — none of the other 9 calls, including 5 Unprotects, produced anything. A second, isolated diagnostic (a fresh process whose *only* DPAPI call was `CryptUnprotectData` against a pre-existing blob) confirmed Unprotect alone does fire the event when it's the first call — ruling out "Unprotect never logs" and confirming "only the first DPAPI call per process logs, regardless of which operation it is" instead. **Consequence: for a long-lived process (browser, password manager, service) that unprotects many credentials over its lifetime, only the very first one is ever observed this way.** State this limitation plainly wherever this telemetry is consumed — don't imply full per-operation coverage.
- **Attribution caveat**: `DataDescription` is the app-supplied, untrusted `szDataDescr` argument to `CryptProtectData` — a careless or malicious caller controls this string directly, it is not proof of which credential store was actually touched. Real "is this a protected credential store" attribution needs to correlate the calling process identity and/or `MasterKeyGUID` against the config domain (§7)/owner-allowlist model (§4), same as every other resource-ownership decision in this design — not something this event's own fields can be trusted for alone.
- **PID attribution bug caught and fixed before shipping (empirically confirmed, not assumed)**: the event's raw ETW `EventHeader.ProcessId` is **always `lsass.exe`** — DPAPI master-key operations are actually carried out by LSASS on the caller's behalf, confirmed by resolving the PID via `QueryFullProcessImageNameW` (`C:\Windows\System32\lsass.exe`, not the calling test process). The first implementation of this wiring set `header.pid` from `EventHeader.ProcessId` the same way every other event type in `etw_consumer.cpp` does, which would have misattributed **100% of DpapiOperation events to lsass.exe** — caught by `test_dpapi_events.cpp`'s own pid-attribution check failing on the first real run, not by inspection. Fixed by parsing the event's own `CallerProcessID`/`CallerProcessCreationTime` properties (the real caller's reuse-resistant composite identity, matching the `(PID, create_time)` discipline used throughout this design) and overriding `header.pid` with `CallerProcessID` specifically for this event type — documented as a deliberate, explicit deviation in `telemetry.h`'s `DpapiOperationDetails` comment, since every other event type's `header.pid` semantics stay as-is.
- **Full property list is 10, not 7** — an earlier diagnostic's own print-bug (attempting to render binary GUID/integer properties as UTF-16 text corrupted the output stream, silently truncating the visible list) hid `CallerProcessID`, `CallerProcessCreationTime`, and `PlainTextDataSize` entirely on the first pass. Re-ran with a name-only enumeration (sidesteps rendering entirely) to get the real, complete list: `OperationType`, `DataDescription`, `MasterKeyGUID`, `Flags`, `ProtectionFlags`, `ReturnValue`, `CallerProcessStartKey`, `CallerProcessID`, `CallerProcessCreationTime`, `PlainTextDataSize`. Lesson for whoever extends this further: don't trust a partial property dump from a naive printer as the complete list — a crash/corruption mid-enumeration looks identical to "no more properties" unless checked explicitly.
- **Test**: `test_dpapi_events.cpp` — calls real `CryptProtectData`/`CryptUnprotectData` from the test process itself (its own first DPAPI call), confirms the event fires, is attributed to the right pid **via the `CallerProcessID` fix above** (this check is what caught the lsass.exe misattribution bug), and reports `return_value == 0`. Deliberately does NOT attempt to prove per-call repetition works, since it's now confirmed that it doesn't.

## Phase 7 — The kernel-mode driver

The large item: real blocking, and the only fully spoof-proof lineage source. Build out `driver_helper.h`'s stub into an actual WDK minifilter project (new subdirectory, e.g. `driver/`), with its own signing/toolchain workstream running in parallel to everything above:

- WDK project setup, EV code-signing certificate procurement, Microsoft Hardware Dev Center / WHCP submission process, a Driver Verifier-based stress-testing loop — this has its own timeline, independent of `core`'s normal release cycle. Start this workstream early; it's very likely the long pole for the whole plan.

Build incrementally — each numbered step below gets its own build + Driver Verifier + stress-test cycle before the next one starts. Do not attempt this as one large change; kernel-mode code is exactly where big-bang delivery causes BSODs and, worse, security holes in the thing meant to prevent them.

1. Driver loads, does nothing harmful — prove the toolchain end-to-end first.
2. `IRP_MJ_CREATE` gate against the config-driven protected-resource list, using Phase 5's canonical-identity resolution (reimplemented as kernel-safe code — user-mode STL can't cross into kernel context directly, needs a kernel-safe subset).
3. `CmRegisterCallbackEx` for registry-key protection, including the hive-file-as-plain-file coverage tie-in (protect the underlying `NTUSER.DAT`-style files via the same IRP_MJ_CREATE gate, not just live registry API calls).
4. `PsSetCreateProcessNotifyRoutineEx2`, keyed on `(PID, PsGetProcessCreateTimeQuadPart(EPROCESS))`, propagating the lineage marker via `PS_CREATE_NOTIFY_INFO.CreatingThreadId` — **never `ParentProcessId`**. This is what supersedes Phase 2's ETW-based interim mechanism as the authoritative source. Validate the exact `PS_CREATE_NOTIFY_INFO` field behavior against the current WDK header before relying on it — don't assume the field layout described in the design doc is exactly right without checking.
5. `ObRegisterCallbacks` against the **Process and Thread object types**, intercepting `OB_OPERATION_HANDLE_CREATE` (covers `OpenProcess`/`OpenThread`) and `OB_OPERATION_HANDLE_DUPLICATE` (covers `DuplicateHandle` — closes the bypass where an attacker duplicates an already-open strong handle from a *different* process instead of opening one directly) against configured owner processes, stripping specific access rights from `POB_PRE_OPERATION_INFORMATION`'s `Parameters->CreateHandleInformation.DesiredAccess` (or `DuplicateHandleInformation.DesiredAccess`) unless the requester is on a short explicit allowlist. **Full rights list, each mapped to the specific technique it closes — don't ship a partial list and assume it's covered by analogy:**
   - `PROCESS_VM_WRITE` + `PROCESS_VM_OPERATION` (both, together — `WriteProcessMemory`/`VirtualProtectEx` need `VM_OPERATION` even when the write itself is blocked, so a lone `VM_WRITE` strip still leaves `VirtualProtectEx`-based tricks such as flipping an existing page executable available) — classic write-then-execute injection.
   - `PROCESS_CREATE_THREAD` — `CreateRemoteThread`/`NtCreateThreadEx` targeting the process. **Missing from earlier drafts of this step — without it, an attacker who can't write a payload can still point a new remote thread at existing code in the target (a real, narrower but genuine technique), so stripping `VM_WRITE` alone is not sufficient.**
   - `PROCESS_VM_READ` — cross-process memory scraping (credential/session-token theft from a protected process's memory, the primary antitheft-relevant scenario for this step).
   - `THREAD_SET_CONTEXT` — `SetThreadContext`-based thread hijacking, and what `QueueUserAPC` itself requires (Win32's `QueueUserAPC` needs `THREAD_SET_CONTEXT` on the handle) — covers APC injection too, not a separate right.
   - `THREAD_GET_CONTEXT` — reading a thread's register state is the normal precursor to the `SetThreadContext` hijack (the attacker needs the original context to redirect execution and often to restore it after). Strip alongside `SET_CONTEXT`, not on its own.
   - `PROCESS_SUSPEND_RESUME` + `THREAD_SUSPEND_RESUME` — the classic hijack sequence is suspend → `SetThreadContext` → resume; leaving suspend/resume rights available even with `SET_CONTEXT` stripped still hands an attacker a free thread-level DoS primitive against the protected process and leaves an adjacent technique open.
   - Handle-duplication, as above — applies to all of the rights in this list, not a separate right of its own.
   
   **Deliberately NOT restricted, to avoid the false-positive/tool-breakage risk already flagged for the registry gate**: `PROCESS_QUERY_INFORMATION`/`PROCESS_QUERY_LIMITED_INFORMATION`, `PROCESS_TERMINATE`, and plain `SYNCHRONIZE`. These grant no write/read/execute-redirection capability against the target and are needed by ordinary monitoring/debugging tooling — restricting them would trade a false sense of extra coverage for real breakage. `PROCESS_TERMINATE` in particular is a *tamper* concern (killing a protected process, not extracting anything from it) — related to step 10's self-protection scope, not this step's injection-prevention scope; don't fold it in here.
   
   This closes what Phase 4's ETW-TI can only detect, not stop, and — because it works by stripping kernel-object access rights rather than hooking a Win32 API — is inherently robust against direct-syscall evasion (unlike a usermode hook, which any caller bypasses by issuing the underlying `Nt*` call directly; see Phase 4's own "usermode hooking rejected" decision for why that path was ruled out generally in this design). It is **not** robust against a fully privileged kernel-mode/BYOVD attacker, who can manipulate `EPROCESS`/`ETHREAD` state directly — same residual-risk framing as step 10.
6. `ObRegisterCallbacks` against the **Token object type** (`OB_OPERATION_HANDLE_CREATE`/`OB_OPERATION_HANDLE_DUPLICATE` on token handles), gating `OpenProcessToken`/`DuplicateTokenEx` chains targeting a configured owner process's token, unless the requester is on the same short allowlist as step 5. **Per `antitheft.md` §10 (added 2026-08-26): Token-object `ObRegisterCallbacks` support is explicitly flagged as not a well-precedented AV/EDR pattern the way Process/Thread interception is (step 5) — feasibility must be validated during implementation, not assumed by analogy.** Build this only after a real feasibility check on a real machine; if `ObRegisterCallbacks` doesn't take a Token major/minor operation the way it does Process/Thread, fall back to whatever Phase 4's token-impersonation detection spike found (Security-auditing-log-based detect-and-revoke) rather than silently shipping with no coverage — and rather than reaching for usermode API hooking as a fallback (see the "usermode hooking rejected" decision in Phase 4): a hook on `DuplicateTokenEx` et al. is trivially bypassed by any caller issuing the underlying syscall directly, so it would add no real coverage, only the appearance of it. This closes the `SeImpersonatePrivilege`-abusing "potato"-family escalation path and the token half of turning an LSASS memory read into a usable impersonated identity.
7. **NEW (added 2026-08-26, reconciling a gap between `antitheft.md` §3's own Windows gap list and this plan — §3 already names "section objects" as a known gap, but no step here ever addressed it until now).** `ObRegisterCallbacks` against the **Section object type**, gating `OB_OPERATION_HANDLE_CREATE` for `NtCreateSection`/`NtMapViewOfSection`-style handles targeting a configured owner process's address space, same allowlist as steps 5-6. This closes the injection family that doesn't go through `WriteProcessMemory`+`CreateRemoteThread` at all — **process hollowing** and **process doppelgänging/"herpaderping"**-style techniques that map a section object into the target instead. Steps 5-6's rights-stripping does not cover this family; it's a structurally different primitive (a memory-mapping object, not a process/thread handle operation), which is exactly why step 5's list, however complete, was never going to be sufficient on its own. **Feasibility is unconfirmed, same caveat as step 6's Token-object work** — `ObRegisterCallbacks` on Section objects is even less precedented in public AV/EDR literature than Token-object interception; validate on a real machine before relying on it, and if it doesn't work, the fallback is ETW-TI's existing (currently PPL/ELAM-blocked, [[core_windows_phase4_etwti_blocked]]) `VirtualAlloc`/section-mapping visibility as a detect-only backstop, not a silent gap.
8. **NEW (added 2026-08-26, same reconciliation as step 7 — `antitheft.md` §3 states plainly "ALPC has no blocking framework at all").** Investigation spike, not a committed implementation step yet: determine whether any real-time interception of ALPC (Asynchronous LPC) traffic is feasible at all for a kernel-mode driver on this OS version, and if so, what the actual mechanism would be — ALPC does not fit the `ObRegisterCallbacks`/`OB_OPERATION_HANDLE_*` model steps 5-7 use, since it isn't gated by a simple object-handle access-rights check the way Process/Thread/Token/Section are. Some LSASS-interaction and EDR-bypass techniques use ALPC directly, and today there is no visibility or blocking of any kind for this channel anywhere in this design. Do not assume a mechanism exists or invent one without a real feasibility check first, same discipline already applied to step 6's Token-object caveat — this step stays a research spike until that check happens, and may resolve to "no practical kernel-level mechanism exists, track as an accepted residual risk" rather than a shippable step.
9. Raw-volume/physical-disk (`\\.\C:`, `\\.\PhysicalDriveN`) coarse allowlist gate — fold into this same driver rather than a separate project.
10. Driver self-protection: PPL (Protected Process Light) status where achievable, tamper-protection against service stop/driver unload by anything less than what Defender requires of itself. State plainly in any accompanying docs that a fully privileged BYOVD/kernel-level attacker remains a residual risk, not something this closes — don't imply otherwise.

**Test at every sub-step, before moving to the next**: `verifier.exe` (Driver Verifier) clean run, plus stress testing under heavy process-creation and file-I/O churn. No sub-step ships to a real test machine, let alone anywhere near a production build, without this.

## Cross-cutting note for whoever picks this up

Every phase above that adds new `core`-side telemetry needs a paired, explicitly-scoped change in `antitheft-agent` (or the future unified `antitheftd`, see `antitheft.md` §2 for the target component structure — there is no OSS/Pro split for this product, see `antitheft.md` §8) to actually consume the new event type. Treat `core/`-side changes as incomplete until that pairing exists — the clipboard bug documented above is the existing proof of what happens when telemetry ships with no consumer.
