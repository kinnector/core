# macOS coverage plan for `core/` — implementation plan for Antitheft

Written on Linux, where none of this can be built or tested — same reasoning as `core/src/windows/WINDOWS_COVERAGE_PLAN.md`. This directory (`core/src/macos/`) didn't exist before this file was written; it needs to be created along with everything in Phase 1 below.

**Unlike the Windows plan, the design here isn't something I had to reconstruct from partial code — it already exists in detail.** Read **`kinnector-context/detection-engine/mac.md`** in full before starting (1087 lines, "Building an Effective macOS EDR Detection Engine") — specifically §2 "Telemetry Model: Hybrid Telemetry Backend (ESF & OpenBSM)" (lines 61-90), which specifies almost exactly what `esf_client.cpp`/`openbsm_parser.cpp`/`macos_ipc.cpp` need to do, down to the specific `ES_EVENT_TYPE_*` events and fallback sequencing. Also read `kinnector.dev/antitheft/antitheft.md` §3 (Enforcement layer) for the Antitheft-specific framing, and note it currently has one inaccurate line (already fixed as part of writing this doc — see the note at the bottom) claiming `core/` already has a working ESF/FSEvents collector. It doesn't; this plan is what builds it.

## Verified current state — this is a from-zero implementation gap, not a from-zero design gap

- **`core/src/macos/` does not exist at all** — confirmed via direct `find`/`ls`, not just a CMake reference check. `ls core/src/` shows only `ffi.cpp`, `ipc.cpp`, `telemetry.cpp`, `linux/`, `windows/`.
- **`core/CMakeLists.txt`** (lines 41-48, 78-89) has a complete-looking Darwin branch — source list (`src/macos/esf_client.cpp`, `src/macos/openbsm_parser.cpp`, `src/macos/macos_ipc.cpp`), `TARGET_OS_MACOS` compile definition, and framework links (`EndpointSecurity`, `Foundation`, `Security`) — but it references files that don't exist. `cmake -B build` on a real Mac would fail at the source-list/compile step today. (A duplicate, equally-stale copy of this same dangling branch exists at `kinnector/src/kinnector-core/CMakeLists.txt` in a separate mirrored tree — don't "fix" that copy by mistake, the live tree is `core/`.)
- **`core/src/ipc.cpp`** (26 lines, read in full) is the clearest contract signal: a clean three-way `#if defined(TARGET_OS_LINUX/WINDOWS/MACOS)` factory in `CreateTelemetrySender()`, expecting a `core/src/macos/macos_ipc.h` declaring `kinnector::macos::MacosTelemetrySender` implementing `ITelemetrySender` — same shape as the Linux/Windows senders that already exist and build. `core/include/kinnector/ipc.h`'s `IPCConfig` already has a comment anticipating this: `std::string socket_path; // Unix domain socket path (Linux/macOS)` — the intended macOS IPC transport is a Unix domain socket, shared with Linux, not something new to design.
- **`core/src/ffi.cpp`** (428 lines, read in full) has **no `TARGET_OS_MACOS` branch anywhere** — every platform `#if`/`#elif` only checks Linux or Windows. On macOS today this file would compile as an inert no-op shell (every platform-specific function falling through to `return false`). This needs a macOS branch added, at minimum for `initialize_telemetry_engine`/`start_telemetry_engine`/`stop_telemetry_engine` to actually stand up the ESF/OpenBSM engine — the Linux/Windows-specific functions (`add_sensitive_inode`, BPF map ops, ETW/driver-helper setup) aren't macOS's concern and should stay platform-scoped as they are.
- **`core/include/kinnector/ipc.h`** and **`telemetry.h`** need no design work — the `ITelemetrySender` interface is already platform-agnostic and complete, and `TelemetrySource::ESF`/`TelemetrySource::OpenBSM` are already defined in the shared wire format (confirmed in `telemetry.h`), just unpopulated on macOS today.
- **`antitheft-agent` (Rust) has zero macOS awareness** — confirmed via grep: no `cfg(target_os = "macos")` anywhere, `Cargo.toml` has only a `cfg(windows)` platform-conditional block, `build.rs` only branches `unix` vs `windows` (macOS falls into the `unix` branch by accident, not by design — it emits a Linux-specific `.so` search path with no `-framework` link flags for `EndpointSecurity`/`Foundation`/`Security`, and would almost certainly fail to link correctly on a real Mac as written today). Unlike Windows, where `antitheft-agent` turned out to have a real head start over `core/src/windows/`, macOS needs both the C++ collector and the Rust consumer side built from nothing — plan for both, not just the `core/` half.
- **`core/README.md`** claims "Utilizes the native Endpoint Security Framework (ESF) and FSEvents" as present-tense fact — same overclaiming pattern the Windows plan found for the ETW line. Its detailed "Architecture & Data Flow" section is explicitly Linux-only. Correct this once the phases below actually land.
- Design references beyond `mac.md` worth knowing about: `kinnector-context/ALERT-SCHEMA.md` has a full worked example alert sourced from ESF (`ES_AUTH_RESULT_DENY` on a Keychain read); `kinnector-docs/CODE-RULEBOOK.md:116` has a one-line summary of the same ESF/auditpipe/`audit_token_t` approach; `kinnector-context/detection-engine/comparison.md` treats ESF/OpenBSM as macOS's telemetry backend on par with ETW and BPF LSM in a cross-platform comparison table.

## What `mac.md` §2 already specifies (summarized — read the full section before implementing, this is not a substitute)

- **Proactive mode**: an `es_client_t`-based ESF client, synchronous `ES_EVENT_TYPE_AUTH_*` hooks (`AUTH_EXEC`, `AUTH_OPEN`, `AUTH_RENAME`, `AUTH_CREATE`, `AUTH_WRITE`, `AUTH_MMAP`) returning `ES_AUTH_RESULT_ALLOW`/`DENY` — this is the actual blocking mechanism, directly analogous to Windows' minifilter/`ObRegisterCallbacks` work and Linux's already-working BPF LSM hooks. Plus `NOTIFY_*` events (`NOTIFY_CONNECT`, `NOTIFY_EXIT`, `NOTIFY_MMAP`) for non-blocking telemetry.
- **Reactive fallback mode**, for when the Endpoint Security entitlement isn't granted (Apple-gated — already flagged in `antitheft.md` §10 as an external dependency to kick off early): attempt `es_new_client`, and on `ES_NEW_CLIENT_RESULT_ERR_NOT_ENTITLED`, fall back to OpenBSM auditing via `/dev/auditpipe` (parsing `audit_token_t`/`AUE_EXEC`/`AUE_EXECVE`/`AUE_CONNECT`/`AUE_OPEN_R` records) plus `FSEventStreamCreate` subscriptions on high-value directories (`~/Library/Keychains/`, `~/Library/LaunchAgents/`, `~/Library/Application Support/`) for file-change telemetry. This fallback is **detection-only** — OpenBSM/FSEvents can't block the way ESF's `AUTH_*` events can, same residual-risk shape as any non-entitled deployment.
- **In-core fast-path containment**: a C++-level rule cache inside `core/` itself, capable of calling `kill(pid, SIGKILL)` directly from the OpenBSM reader thread for zero-tolerance violations, bypassing FFI/agent round-trip latency. This is architecturally significant and different from how Linux/Windows are designed (both push the decision out to the Rust consumer) — preserve this design intent rather than flattening macOS to match the other two platforms' shape.
- **ESF watchdog handling**: ESF auth callbacks have a hard ~30-second kernel watchdog — must return ALLOW/DENY immediately and defer any user-interaction/suspend flow to an out-of-band thread via `SIGSTOP`/`SIGCONT`, never block inside the callback itself.
- **`com.apple.quarantine` xattr** is the macOS analog of Windows' Zone Identifier ADS (already handled crudely via `std::ifstream` on Windows — see the Windows plan's note on `GetZoneIdentifier`) — use the proper `xattr`/`getxattr` API here rather than repeating that same string-hack pattern.
- `mac.md` has dozens of further per-heuristic ESF-mode/OpenBSM-mode implementation notes (lines ~910-1030) mapping specific `ES_EVENT_TYPE_*` events to specific detection heuristics — consult these directly when implementing each phase below rather than re-deriving event mappings from scratch.

## Phases

**Phase 1 — `macos_ipc.{h,cpp}`.** Implement `MacosTelemetrySender : public kinnector::ipc::ITelemetrySender` per the contract `ipc.h`/`ipc.cpp` already define, Unix domain socket transport (shared design with Linux's `LinuxTelemetrySender` — read `core/src/linux/linux_ipc.cpp` for the pattern, including its socket-permission check before trusting the connection, `linux_ipc.cpp:93-101`). **Test**: send a synthetic `TelemetryEvent` end-to-end through the socket, confirm receipt.

**Phase 2 — `esf_client.cpp`, proactive/blocking mode.** ESF client registration, `AUTH_EXEC`/`AUTH_OPEN`/`AUTH_RENAME`/`AUTH_CREATE`/`AUTH_WRITE`/`AUTH_MMAP` hooks per `mac.md` §2, mapped to `telemetry.h`'s existing event types. Respect the watchdog constraint above. **Test**: requires the Endpoint Security entitlement — start the entitlement application process (per `antitheft.md` §10) before this phase can be tested at all, since ESF is unusable without it even in development. Confirm a denied `AUTH_OPEN` actually blocks the underlying `open()` call in a test process.

**Phase 3 — `openbsm_parser.cpp`, reactive fallback.** `/dev/auditpipe` reader, `audit_token_t` parsing, `AUE_EXEC`/`AUE_EXECVE`/`AUE_CONNECT`/`AUE_OPEN_R` record handling, plus the `es_new_client` failure-detection logic that triggers fallback. **Test**: force `ES_NEW_CLIENT_RESULT_ERR_NOT_ENTITLED` (e.g. run without the entitlement) and confirm the engine seamlessly switches to this path rather than failing outright.

**Phase 4 — FSEvents subscriptions.** `FSEventStreamCreate` on the high-value directories listed above, as the fallback mode's file-change telemetry complement (OpenBSM's `AUE_OPEN_R` alone won't catch everything FSEvents would). **Test**: modify a file under a watched directory in fallback mode, confirm the event arrives.

**Phase 5 — In-core fast-path containment.** The direct-`SIGKILL`-from-reader-thread rule cache per `mac.md` §2 — this is a deliberate architectural choice specific to macOS, implement it rather than routing everything through the Rust consumer first. **Test**: configure a zero-tolerance rule, trigger it, confirm containment happens without waiting on an FFI/agent round trip (measure latency against the round-trip path to confirm the fast-path is actually faster).

**Phase 6 — Keychain-specific coverage.** File-level ESF hooks don't cover Keychain items (they're not plain files) — per `antitheft.md` §3's existing note, this needs either `SecItem` API-level interposition or ESF's keychain-specific event types. Needs its own research spike into what ESF actually exposes for Keychain access before committing to an approach.

**Phase 7 — `ffi.cpp` macOS branch + `CMakeLists.txt`/README fixes.** Add the missing `TARGET_OS_MACOS` branch to `ffi.cpp` for engine lifecycle functions. Once Phases 1-4 are real, the `CMakeLists.txt` Darwin branch (already correct-looking) will finally build against real files — verify it actually does. Correct `README.md`'s overclaiming ESF/FSEvents line to match actual state at each milestone, don't leave it perpetually ahead of the code.

**Phase 8 — `antitheft-agent` Rust-side macOS support.** Add `cfg(target_os = "macos")` handling throughout (mirroring the existing `cfg(windows)`/`cfg(unix)` split), fix `build.rs` to actually emit the right `.dylib` path and `-framework` link flags instead of accidentally falling into the Linux-shaped `unix` branch. This is unlike the Windows case — there's no existing Rust-side head start to build on here, budget for this as real, from-scratch work.

## Cross-cutting note

Same principle as the Windows and Linux plans: every phase's new telemetry needs a paired, working consumer in `antitheft-agent` (Phase 8) to be worth anything — don't treat the `core/`-side phases as complete in isolation.
